Architecture

Kafka between every stage

The topics are the system of record. Druid and Redis are views that can be rebuilt, and the services that keep state (pacing, audit) rebuild it from the topics when they start. The audit also queries Druid and Redis directly to compare them.

Decisions that shaped it

Where the money could go wrong, and what prevents it

At-least-once at the edge, exactly-once in the middle

The gateway acknowledges a batch only when Kafka holds every event, and answers 503 otherwise, so the player retries. Duplicates are expected and removed by event ID inside Flink's exactly-once state. The cost is 30 minutes of event IDs held as state.

Privacy at the first hop

Raw device IDs never reach Kafka. The gateway replaces them with a keyed hash when the viewer consented and drops them when not; rotating the key unlinks history.

Event time, with lateness built in

Delivery counts in the minute the ad played. Windows accept events 10 minutes late and re-emit corrected totals; a custom trigger cut one minute's revisions from 217 to 6.

Invalid traffic is flagged, not deleted

A device above a plausible impression rate is marked and excluded from spend but kept, because billing disputes need the evidence.

The ad server degrades instead of collapsing

Admission control refuses excess requests at once, so the player can fill the break. Before it, overload hung the server with 13,062 connections stuck.

Pacing from two clocks

Delivered spend is exact but a minute old; served spend is immediate but overstates. The pacer budgets with one and steers with the other, and every uncertainty resolves towards stopping early: under-delivery can be made good, overspend cannot.

Shared counters as absolute values

Each ad server writes its own running total per line item (HSET, a field per instance) and readers sum the fields. A failed or retried write can neither lose nor double-count spend.

Prove the money continuously

A system can be up, fast and wrong. The audit compares records of the same fact produced by different code and pages with the line items named when they disagree.

A Flight Recorder profile at saturation found 14% of Flink's CPU compressing small Kafka batches; larger batches cost no visible latency under exactly-once and gave 7% more throughput. The next lever is serialization across the job's four keyed shuffles, about a quarter of its CPU.

Bugs only measurement found

Twelve bugs no unit test caught

Each was found by reconciling, profiling or deliberately breaking the running system. Each is fixed, and most now have a unit or alert-rule test that reproduces them.

  1. Late-window spam. One minute was revised 217 times by late events.
    reconciliation
  2. Lost event time. Records released from Flink's broadcast state missed their windows.
    reconciliation
  3. A replay that looked like data loss. The seed was not passed on, so event IDs repeated and were correctly de-duplicated.
    crash drill
  4. The ad server hung under overload. Unbounded work left 13,062 connections stuck and exhausted file descriptors.
    load sweep
  5. The campaign catalog was never published. A zero send timeout failed every write until metadata arrived; 82k events went unenriched.
    reconciliation
  6. Pacing overspent by up to 51% after a cold start. It chased a partial period and carried a throttle across the boundary.
    live run
  7. A guessed constant under-delivered by 6%. Serve-to-play delay was assumed 30 s; measured, it is 15 s.
    live run
  8. The pacing fallback could have overspent by 20%. It assumed 20% of served ads go unplayed; the live figure was 1–4%.
    live run
  9. Spend increments were dropped under load. Counters ran 3–6% low and 21 line items went over budget.
    audit, first run
  10. A false page during recovery. A stale-checkpoint alert fired as soon as its cause stopped holding it back.
    failure drill
  11. A full disk took the system down unannounced. Time-only retention filled it; Redpanda crashed and Flink crash-looped with no alert naming the cause.
    load test
  12. 14% of Flink's CPU went on compressing tiny batches. Bigger batches cost no visible latency under exactly-once.
    profile

What production would add

Beyond one machine

  • Multi-node everything. Kafka with three replicas across zones, Flink with HA and remote checkpoints, Druid deep storage, Redis replicas.
  • Schemas as contracts. A schema registry and a binary format instead of versioned JSON, roughly halving bytes per event.
  • Billing-grade reporting. A daily batch recomputation as the invoice of record, with streaming totals as the fast estimate, reconciled.
  • Ad serving at the edge. Regional ad servers and frequency caps, budgets reconciled globally by the pacing service.
  • Identity. Single sign-on for the dashboard and per-advertiser access to data.
